# grandMA3 MCP Bridge (onPC)

Target build: grandMA3 onPC 2.5.1.0.

This directory contains an onPC-only grandMA3 plugin and an MCP server. The AI client launches the MCP server and chats in its own AI window; running the plugin in the showfile enables the MCP tools to reach grandMA3.

## Layout

- `grandma3_ai_assistant.lua` — import as a grandMA3 ComponentLua.
- `grandma3_ai_assistant.xml` — importable plugin manifest.
- `companion_server.py` — MCP stdio server; Python standard library only.
- `start_grandma3_mcp.sh` — Bash launcher for the local MCP server (tunnel mode is optional).
- `tools/sync_api.py` and `api_index.json` — parsed HelpLua function list used for API drift checks.
- `journal.json`, `snapshots/` — generated: change history and pre-change object exports.
- `mvr.py`, `patterns.py` — MVR reader / stage estimator and the position-pattern learner.
- `position_patterns.json`, `stage.json` — generated by the pattern and stage tools.
- `tests/` — MCP/journal tests (`python3 -m unittest discover -s tests`) and host-side Lua tests (`cd tests && lua test_grandma3_ai_assistant.lua`).

## Install

1. Register `python3 companion_server.py` as an MCP server in the AI client. It uses stdio and does not need an AI provider key; the AI client supplies its own model and credentials.
2. In grandMA3 onPC, import `grandma3_ai_assistant.xml` or paste the Lua component into a Plugin Pool object.
3. Run `Plugin <number> "Start"` once in the showfile. The plugin listens only on `127.0.0.1:17844`.
4. In the AI window, call `ma3_status` to verify the bridge, then use `ma3_context` and `ma3_execute` to inspect and change the show.

For local use, start the MCP server directly from the onPC computer:

```bash
./start_grandma3_mcp.sh
```

The script checks `127.0.0.1:17844` and launches the stdio MCP server. This local mode does not require `tunnel-client`, a Control Plane API key, or internet access. Use `--doctor-only` to validate without starting the long-running process. The existing tunnel workflow remains available explicitly with `--tunnel --tunnel-id tunnel_your_id`.

The MCP server forwards tool calls to the running Lua plugin. `ma3_execute` previews actions when `confirm=false`; the AI client should show that preview and call it again with `confirm=true` only after user approval.

## Available MCP tools

Seeing the show (read-only, paged with `limit`/`offset`):

- `ma3_status`, `ma3_context` - bridge state, selection (subfixture index + selection-grid x/y/z), selected sequence.
- `ma3_api` - search the live Lua API of the running build (`GetApiDescriptor`/`GetObjApiDescriptor`), list `Enums`, and with `drift=true` compare against `api_index.json`.
- `ma3_inspect` - any object by address or `H#` id: class, every property, children.
- `ma3_list` - `ObjectList` patterns or the (recursive) children of a base object.
- `ma3_fixtures` - fixtures from the selection, a group, or the whole patch, with properties and selection-grid position.
- `ma3_sequences` - sequences, cues, which one is selected, the current cue.
- `ma3_presets` - preset pools, preset data (`GetPresetData`/`Fast`), programmer phasers.

Changing the show:

- `ma3_execute` validates and executes `cmd`, `set`, and `wait` actions (preview with `confirm=false` first).
- `ma3_lua` runs any Lua with the full console API (see below).
- `ma3_journal` / `ma3_rollback` list and undo what the AI changed.

Workflows and notes: `ma3_teach_start`, `ma3_teach_record`, `ma3_teach_stop`, `ma3_workflow_save`, `ma3_workflow_run`, `ma3_notes`.

## MVR stage data and position patterns

For positions the server reads the real stage instead of guessing it. Pure standard-library Python (`mvr.py`, `patterns.py`):

1. Ask the user for an **MVR export that contains the scenic data (stage deck, trusses, screens) and the fixtures**.
2. `ma3_mvr_load` reads it (matrices composed through groups; fixtures with FixtureID, GDTF spec/mode, world position and home beam direction; scenic objects with a bounding box when the zip carries a `.glb` or `.3ds` model).
3. `ma3_mvr_stage` estimates the deck bounds, centre, size, deck height and **audience direction**, says how it decided and how confident it is, and asks to be told (`stage_names`, `audience`) when it only guessed. Saved to `stage.json`.
4. `ma3_mvr_align` matches MVR `FixtureID` to MA3 `FID` and computes the rotation/offset between the file and the patch, with residuals, so the stage can be used in patch coordinates.
5. `ma3_mvr_fixtures` lists the fixtures in the stage frame (u across, v toward the audience, h above the deck).

Patterns are learned from presets the user programs by hand. When the user says the positions are done: save the show, then run `ma3_patterns_extract` with the preset numbers and group numbers. It exports those presets to XML, converts every pan/tilt into where the beam lands relative to the stage, and writes `position_patterns.json` per preset x group x selection-grid row (landing depth, mean tilt, and a lateral rule: landing across-stage = slope x fixture across-stage + offset; 1 = parallel, 0 = converge, above 1 fan out, below 0 cross). `ma3_patterns` reads them and `ma3_patterns_generate` applies a pattern to any group and returns Pan/Tilt per fixture without touching the show.

Conventions are in `MA3_PLUGIN_DEVELOPMENT.md` (hanging fixtures: Pan 0 / Tilt 0 is straight down, audience at -Y, grid row 0 is the front row). The default stage (centre 0,2, audience -Y) is an unconfirmed estimate used only until an MVR stage is loaded.

## ma3_lua and rollback

`ma3_lua` is open execution: it runs immediately with the whole console API. Every call is recoverable:

1. It runs inside one Oops group (`CreateUndo`/`CloseUndo`, closed even on error). `UndoDisable` is blocked.
2. Inside the snippet `Cmd`/`CmdIndirect`/`CmdIndirectWait` default to that undo handle, and `Create/Append/Insert/Delete/Remove/Copy/Acquire` get it injected. `Set` is wrapped so the old value is recorded.
3. `touches=[addresses]` exports those objects first (snapshot). `inverse=<Lua>` is stored and runs on rollback.
4. The MCP server writes each call to `journal.json` (code, strategy, flags). `ma3_rollback` replays it: Oops when the entry is the newest undo group this plugin created, then the recorded property values, snapshots and the inverse script.

Limits: Oops is a stack, so older entries cannot be undone while newer ones exist (roll back newest first, or pass `force_oops`). Snippets that use `Export`, `Save`, `SetVar`, `Keyboard`, `Mouse`, `RemoteCommand` and similar are flagged because Oops cannot undo them. Direct handle writes other than `Set` and the injected structural calls need `touches` or `inverse`. If the plugin restarts, undo ids reset and Oops entries from before the restart are skipped.

The injected helper table `ma3` offers `h`, `props`, `children`, `find`, `walk`, `fixtures`, `aim`, `split`, `cmd`. `tools/sync_api.py` rebuilds `api_index.json` from the console's `HelpLua` export.

The plugin bridge listens only on `127.0.0.1:17844`. Set `GRANDMA3_AI_PLUGIN_HOST` and `GRANDMA3_AI_PLUGIN_PORT` in the MCP process only for local troubleshooting; exposing the bridge to a network is intentionally unsupported.

The plugin creates an Oops group for every confirmed action batch, limits command length and batch size, and reports command results. Workflow data, the change journal and AI credentials are kept outside the showfile.

The MCP automatically appends `/noconfirm` to each console command before sending it, including every command in semicolon/newline batches. Quoted text and existing `/noconfirm` options are preserved; explicit `/confirm` options are removed. This applies to action/workflow commands and to runtime `Cmd`, `CmdIndirect`, `CmdIndirectWait`, and `ma3.cmd` calls in Lua snippets, including inverse Lua used for rollback. The Lua wrappers live only in the request environment and preserve the plugin's undo handling. MCP `confirm=false` still previews and `confirm=true` executes; this setting is separate from console dialogs. Restart the MCP process to load changes; no plugin re-import is required. Commands stored inside console macros and commands generated internally by the existing plugin are outside this transport policy.

Always test in a copy of the showfile and verify behavior against the exact grandMA3 onPC version in use. MA Lighting does not guarantee plugin compatibility across software releases.
